---
title: Develop a Starling plugin
description: Use the current host interfaces and examples for a server plugin.
---

Build against the plugin API shipped with the Starling release you target. Starling's host exposes scoped configuration, membership, permissions, channel operations, and messaging to native libraries and WebAssembly components.

Start from the native and WASM examples in the [Starling repository](https://github.com/Fancy-Mumble/starling). Match their ABI and component interface versions. Keep plugin messages opaque to the host and validate every payload in the plugin that owns it.

Test loading, registry advertisement, connect and disconnect events, permission failures, restart behaviour, and enable/disable cycles. A native plugin executes inside the plugins service process; WebAssembly has a different capability boundary and must be tested separately.

Read the [plugin host plan](https://github.com/Fancy-Mumble/starling/blob/main/docs/PLUGIN-HOST-PLAN.md) for implemented host calls and remaining gaps before depending on a capability.
